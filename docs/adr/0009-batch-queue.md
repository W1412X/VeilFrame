# ADR-0009：批量队列按独立会话执行，复核导出保持人工

- 状态：Accepted
- 日期：2026-11-21
- 关联：ADR-0008、`vf-queue`、`app/src-tauri/src/batch.rs`

## 背景

设计文档里的批量队列包含检查点续扫和自动导出。真正实现时，如果队列和编辑器共用同一个会话，队列扫描期间用户就无法复核；如果做断点续扫，则需要把扫描器的中间状态序列化，成本远高于收益。用户当前的使用方式是「导入一批视频，扫完逐个检查，再导出」。

## 决策

1. 队列在内存中保存，关闭应用即丢失；不写队列持久化文件。
2. 每个任务使用独立的 `Session`，在后台 `std::thread` 中串行执行。加入队列时把当前项目启用的目标克隆一份，之后编辑器的修改不影响已入队任务。
3. 扫描开始前先把项目保存为视频同目录的 `<视频名>.maskproj`；重名时追加 `-2`、`-3`，不覆盖已有文件。扫描过程中每次自动保存都写这个文件，因此取消或崩溃时已经扫出的段落仍然保留。
4. 取消在当前目标边界生效，已完成的段保留，任务进入 `cancelled`，可从队列重新排队（重新扫描整段，不使用检查点）。
5. 失败自动重试，最多 2 次；仍失败则停在 `failed`，由用户手动重试。
6. 扫描成功后任务停在 `review`，不自动导出。用户从队列打开任务，项目进入编辑器复核；普通导出命令带可选 `queue_job` 参数，导出成功后把该任务标记为 `done`。
7. 队列事件 `vf-queue-changed` 推送完整的 `JobView[]`，前端不自己推算状态。

## 理由

- 独立会话让队列和编辑器互不阻塞，也避免一个 `Mutex<Session>` 同时承担两种角色。
- 项目物化到视频旁边，取消、崩溃、跨天继续处理都有落点，符合「文件即状态」的现有设计。
- 人工复核是打码工具的正确默认：误检漏检需要人判断，自动导出会把错误结果直接产出。

## 代价

- 应用重启后队列为空；需要重新添加视频（已扫描出的 `.maskproj` 可以直接用「打开项目」继续）。
- 只有一个工作线程，批量任务不并行；这样避免了多个 OCR/OpenCV 实例争抢内存。
- 重新排队会整段重扫，检查点只在 `vf-queue` 数据模型里保留，尚未用于续扫。
- 不做批量自动导出，导出仍需逐条确认。

## 备选方案

- **队列与编辑器共用会话**：实现简单，但队列扫描时编辑器不可用，且复核需要等整批结束。
- **断点续扫**：需要扫描器输出并恢复逐目标、逐帧的中间态，当前收益不足，留待真实需求出现。
- **自动导出**：与人工复核的产品定位冲突，暂不做。
